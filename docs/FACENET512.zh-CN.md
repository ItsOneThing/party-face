# FaceNet512 升级与测试

这是模型升级代码，不会自动覆盖现有活动或把旧索引转成新模型。公开站点只有发布新版本后才会支持新活动。

## 先在本机验证

1. 运行 `python3 tools/download_models.py` 和 `python3 tools/download_facenet.py`。新模型约 94 MB，下载脚本校验固定 SHA-256；ONNX Runtime Web 固定为 1.22.0。
2. 用原方式启动 `python3 tools/server.py`，打开 <http://127.0.0.1:8765/model-lab.html>。
3. 点“先验证模型运行”，只使用合成输入，验证浏览器能生成归一化 512 维向量。
4. 使用明确同意参加识别测试的人物照片，选一张单人自拍和若干正确/错误候选照片，对照结果。页面不调用 Supabase 或 Drive，也不保存或上传照片或特征。

## 接入 Supabase 与新活动

1. 已完成 001–003 的项目，在 Supabase SQL Editor 执行 `supabase/migrations/004_facenet512.sql`。它保留旧索引，允许 128/512 维共存并检查活动对应维度。新项目依次执行 001–004。
2. 部署仓库内新版 `supabase/functions/search-photos/index.ts`，继续使用现有 ALLOWED_ORIGINS、RATE_LIMIT_SALT 与密钥配置。只部署函数、不执行 004，会导致新导入失败。
3. 发布新版访客站点。GitHub Actions 会下载新模型和运行时；管理工具和本地测试页不会发布。
4. 管理页用**新的活动编号**（例如 facenet-test-2026）和已明确获得人脸检索同意的测试照片文件夹。人脸索引默认关闭；确认具备授权后再开启。
5. 重新导入建立 512 维索引。旧 128 维特征必须从照片重新计算；旧活动编号会被拒绝，避免混用。
6. 测试正确和错误匹配、手机加载速度，再开放新活动。旧活动不会自动关闭；如需停止旧识别查询，仍要单独在管理工具处理。

## 评估与限制

模型标识：`facenet512-onnx-ssd68-align5-prewhiten-l2-v1`。SSD + 68 点定位，五点相似变换对齐，RGB 160×160，逐图片标准化，FaceNet512，L2 归一化，再使用欧氏距离。

0.75 是未校准的初始距离阈值，不能理解为 75% 准确率。记录真正属于参考人物的照片、错误照片和漏掉照片；先用一批校准，再用另一批验证。检测器仍采用 face-api.js 的 SSD，因此远处小脸、侧脸、遮挡或暗光仍可能漏检。多张脸的照片取最近距离，可能误匹配。

94 MB 模型会增加首次流量与手机内存压力；浏览器通常会缓存，但不能承诺缓存始终存在或所有手机几秒完成。单线程 WebAssembly 不要求 GitHub Pages 配置跨域隔离。推理在浏览器完成，不引入付费云端识别 API，平台配额和流量限制仍适用。

活动照片的人脸索引涉及生物识别数据。此前只有拍照/分享说明的照片不能因为用户上传自拍就视为获得全部被拍摄者的识别授权。取得相应授权并解决隐私要求前，使用纯本地已同意的测试照片评估。

模型与第三方许可证见 `THIRD_PARTY_NOTICES.md`。免费/开源不意味着可以任意使用训练数据或活动照片。


## 本地人物分组预览（实验）

打开 <http://127.0.0.1:8765/person-groups.html>，先用少量已取得明确同意的测试照片。浏览器提取每张人脸的特征和裁剪，按保守距离阈值 0.65 分组。新成员必须与所有组员在阈值以内；两个候选组同样接近时独立成组，同一合照中不同人脸不得自动归同组。结果仍可能错误、分裂，且会受照片输入顺序影响。这不是已验证的身份聚类系统。

“查看纠错界面示例”使用示意图，不需要真人照片，不进行识别。检查每组的人脸与对齐裁剪；选中两个组可合并，错误人脸可移到其他组或独立成组。人工合并不受相似度阈值限制，但仍阻止同一照片的多张脸进入同组。每组可以查看关联的原照片；合照可关联多个组。

分析中可要求处理完当前照片后暂停；再次分析会从选择的照片重新生成结果并替换本轮纠错。最多 500 张照片、2000 张人脸，每张最多 20 MB。分组和纠错仅存于当前页面内存，清空、刷新或关闭即丢失，不持久化到数据库或本地存储。不上传照片或特征，不会修改现有活动、自拍查询和公开站点。分组质量确认后才考虑接入查询，不能把小组待核对结果直接当作可靠身份。


## 接入分组查询

以上纯本机实验模式仍不保存活动数据。现已另加“读取已导入活动、保存草稿、发布分组”的管理模式，需要 005 数据库迁移，见 [人物分组保存与发布指南](PERSON_GROUPS.zh-CN.md)。两种模式的保存行为不同；公开站点须部署新版 Edge Function 与网页才会使用已发布分组。
