# 人物分组保存、发布与自拍查询

参加者仍只上传一张自拍。组织者先导入活动照片，纠正人物分组，保存草稿，最后发布。自拍匹配到已核对的人物组后，返回这个组关联的去重照片，包括手动关联的侧脸照片。

## 一次性升级

1. 先完成 FaceNet512 升级：在 Supabase SQL Editor 依次执行尚未运行的 004 和 `supabase/migrations/005_person_groups.sql`（已有 001–003 则不重复执行）。新项目依次运行 001–005。
2. 将 `supabase/functions/search-photos/index.ts` 的完整新版代码部署到原 `search-photos` Edge Function，继续使用已有 Secrets。005 必须先执行，新版函数会读取新增的分组版本字段。
3. 发布升级分支的访客网站。当前代码在 GitHub 草稿 PR，不会自动部署 main；合并并完成 GitHub Pages 发布后才上线。组织者管理页、分组页不发布到 Pages。
4. 重启本机 `tools/server.py`。密钥留在本机 `.env`，后端管理凭证不会进入访客网页。

## 每次活动

1. 在 `admin.html` 创建新的 FaceNet512 活动，导入已明确取得人脸检索与分组授权的照片。等导入完成再分组。旧的 128 维活动不能直接使用。
2. 打开 <http://127.0.0.1:8765/person-groups.html>，填写同一个活动编号，确认照片人物已获知且同意相关处理，点“读取已导入活动”。本机必须保存该活动的访问码；不要发密钥到聊天或公开仓库。
3. 没有草稿时会自动保守分组；有与当前索引一致的草稿时恢复最新草稿。截图预览来自私有缩略图，原图可跳转 Drive。已导入索引没有保存对齐裁剪，不能用缩略图裁剪证明原模型对齐正确。
4. 检查人脸，合并同一个人的多个组，移出错误人脸；同一张合照的不同人脸不允许归入同组。每组确认无误后，点“确认这一组是同一个人”。
5. 点“保存分组草稿到 Supabase”。保存只创建私有快照，不改变已发布的版本；再次读取活动可恢复。未保存的编辑仍会在刷新后丢失。
6. 点“发布已核对的分组”。发布的是已保存快照；未核对组不返回照片。它们仍作为相似度歧义检查的候选，避免把未核对的人误认成已核对的人。发布至少需要一个已核对组。
7. 分组发布不自动开放活动。若活动尚未开放，在管理工具另行开放，再分享完整活动链接。参加者照常选一张自拍，不会看到分组管理操作。

## 查询规则与限制

查询对各组全部人脸样本取最小距离。最接近的组必须已核对、距离不超过该活动阈值（新模型起始值 0.75），且与第二候选组至少相差 0.08；否则不返回分组照片。阈值和间隔仍需用独立、已获同意的样本校准，不能据此承诺准确率。

发布分组前，活动沿用直接人脸匹配；发布后改用人物组匹配。相册浏览功能不变，持有完整活动链接的人仍能浏览整个相册，自拍不是身份验证。错误合并可能扩大误匹配，发布前必须核对。

重新导入替换人脸记录会使旧快照过期。过期分组查询会失败，不会悄悄退回直接匹配；需重新读取、核对、保存并发布。索引变化时旧草稿不自动恢复，防止错误关联。

本机照片选择模式与示意图模式仍只是本地实验，不能直接保存到活动；保存功能只对读取的 Supabase 活动索引启用。当前每个活动预览最多 500 张照片、2000 张人脸。每次保存保留一个快照，长期使用应由组织者制定旧草稿和生物识别索引的保留与清理安排。

数据库表启用 RLS，访客不能读取人物组、人脸特征或草稿。访问活动需要原活动链接访问码，管理写入还需本机服务与本机活动凭证。此代码不能替代必要的授权、隐私说明和数据保留安排。

## 当前验证状态

本地数据库集成测试覆盖：正脸命中返回手动关联的侧脸照片、未核对组排除、相似候选拒绝、保存不发布、发布版本隔离、跨活动拒绝、权限、索引过期和模型维度。Edge 与本机管理接口使用模拟后端测试。真实云端迁移、部署和真实照片质量还需实际验证；本次代码修改没有自动操作旧活动数据。
